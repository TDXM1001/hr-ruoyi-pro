# 不动产处置关联最小闭环第五批设计

## 1. 背景

前四批已经把不动产详情壳侧的处置关联做到了“能判断状态、能跳转联动、能识别责任归口”。

当前剩余问题不是业务规则缺失，而是前端首屏口径仍分散在三处：

1. 详情壳顶部摘要只展示简化状态。
2. 总览正文单独展示处置闭环摘要。
3. 处置页签首屏又拆成摘要卡和联动卡。

这种结构会让资产管理员在同一资产详情内看到多套相似但层级不一致的提示。

## 2. 本批目标

第五批只做一件事：把“处置状态 + 责任归口 + 下一步动作 + 联动入口”统一成同一套处置闭环卡视图。

实现后要满足：

1. 顶部摘要、总览、处置页签使用同一套处置闭环解释数据。
2. 处置页签首屏不再拆成“摘要卡 + 联动卡”两层，而是一张闭环卡承载。
3. 生命周期轨迹和处置记录卡片继续保留，但退到支撑信息层。
4. 本批继续只做前端隔离层，不修改处置后端脏文件。

## 3. 方案选择

### 方案A：闭环卡统一型（采用）

做法：

1. 在处置解释器中新增统一的 `DisposalClosureCard` 视图模型。
2. 顶部摘要使用闭环卡的紧凑表达。
3. 总览正文和处置页签使用同一张共享处置闭环卡组件。
4. 处置页签把“进入资产处置 / 发起处置”按钮合并到闭环卡底部。

优点：

1. 统一口径最直接。
2. 不新增后端依赖。
3. 改动集中在不动产详情壳隔离层。

### 方案B：只改顶部摘要文案

优点：改动最小。

缺点：总览与页签仍然是两套组件，后续还会继续分叉。

### 方案C：单独新增处置总览接口

优点：边界最干净。

缺点：当前批次完全没有必要，会跨到后端和现有处置脏文件。

## 4. 设计结果

### 4.1 统一视图模型

在 `disposal-overview.ts` 中新增 `DisposalClosureCard`，由现有 `DisposalOverviewSummary` 派生：

1. 当前闭环状态
2. 当前责任归口
3. 责任动作
4. 最近处置动作
5. 最近责任人
6. 下一步建议
7. 发起入口配置
8. 顶部摘要用的紧凑标题与紧凑说明

### 4.2 顶部摘要收口

详情壳顶部摘要中，“处置闭环”不再只显示一个状态词，而改为：

1. 主值：`状态 + 责任归口 / 责任动作`
2. 副说明：`最近动作 + 最近责任人`

这样资产管理员留在详情页首屏，也能先判断“现在谁负责推进”。

### 4.3 总览正文收口

总览中的“处置闭环摘要”改为复用共享闭环卡组件，展示：

1. 当前闭环状态
2. 最近处置动作
3. 当前责任归口
4. 责任动作
5. 最近责任人
6. 最近动作说明
7. 责任提示
8. 下一步建议

### 4.4 处置页签收口

处置页签首屏改为同一张共享闭环卡，底部直接挂载：

1. 发起处置
2. 进入资产处置

原“处置联动”单独卡片取消，避免首屏重复。

### 4.5 保留项

以下内容继续保留，不在本批做行为变更：

1. 生命周期里的处置节点责任视图
2. 处置记录卡片里的责任归口视图
3. 跳转统一处置页时的上下文参数

## 5. 风险与控制

### 5.1 风险

1. 总览、页签、顶部摘要共用解释层后，容易把现有旧测试打碎。
2. 处置页签去掉“处置联动”卡后，需要确认入口仍然可见。

### 5.2 控制

1. 先补红灯测试，再做实现。
2. 只改不动产详情壳组件和解释器，不碰统一处置后端文件。
3. 保持原有跳转参数不变，避免影响处置主页面。

## 6. 验收标准

1. 顶部摘要能显示统一后的处置紧凑摘要。
2. 总览处置卡和处置页签首屏能显示相同的责任归口、责任动作和下一步建议。
3. 未发起处置场景下，处置页签首屏仍能直接看到“发起处置 / 进入资产处置”。
4. 定向测试与相关回归测试全部通过。
