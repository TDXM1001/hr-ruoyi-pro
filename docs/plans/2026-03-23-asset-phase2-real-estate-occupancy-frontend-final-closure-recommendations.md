# 2026-03-23 不动产占用前端最终收口建议

## 1. 文档目的

这份文档用于回答一个现实问题：

> 不动产占用前端已经做了很多，接下来到底该停在哪里，怎样才算“收口完成”。

它不是新一轮功能设计文档，而是一份阶段性收口建议，目标是帮助团队统一判断：

1. 占用前端哪些能力已经够用
2. 哪些能力应该保留在主视图
3. 哪些能力应该明确下沉到治理工具区
4. 哪些能力后续不建议继续追加

## 2. 当前判断

## 2.1 业务闭环已经完成

从业务角度看，占用模块当前已经具备最小闭环：

1. 发起占用
2. 变更占用
3. 释放占用
4. 主档回写
5. 历史留痕

这意味着占用前端已经不再是“缺主流程”，而是进入“结构收口与维护治理”阶段。

## 2.2 当前真正的问题不在业务功能，而在层次感

用户当前的真实困惑不是“不能操作”，而是：

1. 页面看起来功能很多
2. 不容易一眼看出主流程
3. 高级治理能力容易抢占主阅读路径
4. 主面板脚本过重，后续继续叠功能会越来越难维护

所以后续占用前端的目标不应该再是继续扩点，而应该是：

1. 收层次
2. 收职责
3. 收预期

## 3. 最终收口原则

建议把占用前端的最终收口原则固定为下面 4 条：

### 3.1 业务优先

主视图只表达资产管理员最常用、最直接的业务动作：

1. 当前是否有有效占用
2. 当前谁在用
3. 下一步能不能发起、变更、释放
4. 最近怎么变更过
5. 历史轨迹怎么查

### 3.2 治理下沉

所有不属于日常主流程的增强能力，统一视为治理工具：

1. 来源链路统计
2. 趋势图
3. 批注视图
4. 导出字段
5. 预设导入导出
6. 快照与审计能力

这些能力可以保留，但不能继续占据主视图中心区域。

### 3.3 脚本分层

占用前端后续只允许两类状态继续存在：

1. 业务状态
2. 治理状态

不再允许在 `occupancy-panel.vue` 里继续堆新的“第三类混合状态”。

### 3.4 阶段止损

在处置主线、审批主线、集成主线尚未补齐之前，不建议继续无限扩展占用治理功能。

占用这条线已经足够细，再继续横向加点，会挤压真正还没闭环的主线开发。

## 4. 最终页面结构建议

## 4.1 第一层：业务操作区

保留，且保持首屏优先。

应长期保留：

1. 当前有效占用卡片
2. 发起占用
3. 变更占用
4. 释放占用
5. 当前状态提示
6. 跨页签联动入口

这一区不应该再引入任何新的统计、预设或审计功能。

## 4.2 第二层：管理摘要区

保留，但控制数量。

建议长期只保留：

1. 主档联动摘要
2. 最近一次变更摘要
3. 状态矩阵

不建议继续往这里叠新的摘要卡片，否则它会重新变成“半分析区”。

## 4.3 第三层：历史轨迹区

保留，而且是主流程的一部分。

建议长期保留：

1. 状态筛选
2. 时间筛选
3. 排序切换
4. 轨迹列表
5. 轨迹焦点定位
6. 趋势钻取后的历史联动提示

这一区的定位应始终是“业务轨迹”，不是可视化报表。

## 4.4 第四层：治理工具区

保留，但默认折叠。

建议统一归档：

1. 来源链路统计
2. 趋势图与趋势窗口
3. 快照管理
4. 重置记录
5. 治理活动流
6. 导出字段配置
7. 自定义预设
8. 导入预览与冲突策略
9. 策略模板管理
10. 治理审计包导出

这一区的目标是“需要时可进入”，不是“默认就打在用户眼前”。

## 5. 最终代码结构建议

## 5.1 推荐固定结构

建议把当前结构稳定为：

```text
occupancy-panel.vue
├─ OccupancyBusinessSection.vue
├─ OccupancySummarySection.vue
├─ OccupancyHistorySection.vue
├─ OccupancyGovernanceSection.vue
├─ useOccupancyState.ts
└─ useOccupancyGovernance.ts
```

这是当前最适合收口的结构，不建议再随意推翻。

## 5.2 各层职责建议

### `useOccupancyState.ts`

长期负责：

1. 当前占用识别
2. 最近释放识别
3. 主档联动摘要
4. 最近变更摘要
5. 历史筛选与排序
6. 轨迹定位

### `useOccupancyGovernance.ts`

长期负责：

1. 治理工具区开关状态
2. 来源链路统计
3. 趋势窗口
4. 趋势钻取
5. 快照保存/恢复/删除
6. 重置记录
7. 治理活动留痕

### `occupancy-panel.vue`

最终应尽量只保留：

1. 视图编排
2. section 接线
3. 少量治理编排逻辑
4. 必要的导出装配逻辑

如果后续继续重构，优先级应该是继续减轻 `occupancy-panel.vue`，而不是继续增加页面能力。

## 6. 建议保留与建议冻结

## 6.1 建议保留

这些能力建议作为最终版保留：

1. 当前有效占用卡片
2. 主档联动摘要
3. 最近变更摘要
4. 历史轨迹筛选
5. 治理工具区折叠入口
6. 来源链路统计
7. 趋势快照
8. 重置记录
9. 策略模板
10. 治理审计包

原因是：这些能力已经形成完整层次，不再是零散增强点。

## 6.2 建议冻结

建议从现在开始冻结下面这类新增诉求：

1. 再新增新的摘要卡
2. 再新增新的趋势维度图表
3. 再新增新的主视图入口按钮
4. 再把治理能力抬回主视图首屏
5. 再给占用页签增加新的分析模块

原因是：继续加这类能力，边际收益已经明显下降。

## 7. 当前最合理的止步点

建议把当前阶段的“占用前端完成定义”定为：

### 7.1 业务上

1. 发起、变更、释放持续可用
2. 主档联动摘要与历史轨迹稳定可读
3. 不需要进入治理工具区，也能完成日常管理动作

### 7.2 页面上

1. 首屏是业务阅读路径
2. 治理工具区默认折叠
3. 用户不再被大量治理功能干扰

### 7.3 代码上

1. `useOccupancyState.ts` 与 `useOccupancyGovernance.ts` 边界稳定
2. `occupancy-panel.vue` 继续减重，但不再承担状态中心职责
3. 后续若继续拆，只拆治理编排，不再动主流程边界

## 8. 后续优先级建议

如果从整个不动产主线来判断，建议后续优先级如下：

1. 占用前端继续做“轻度收口”可以
2. 但不建议继续大规模加功能
3. 更建议把精力切回：
   - 处置关联最小闭环
   - 审批主线回写
   - 集成主线

也就是说：

> 占用模块现在更适合进入“维护与收口模式”，而不是“持续扩展模式”。

## 9. 最终建议

一句话结论：

> 占用前端现在应该收住，不该再继续无限扩张；保留现有主流程与必要治理能力，把高级功能固定归入治理工具区，并把后续研发重心切回其他尚未闭环的主线。

这就是当前最稳、最省返工、也最符合整体二期推进节奏的收口方案。
