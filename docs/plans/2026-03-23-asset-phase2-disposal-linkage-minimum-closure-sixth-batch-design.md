# 不动产处置关联最小闭环第六批设计

## 1. 背景

第五批已经把不动产详情壳顶部摘要、总览正文和处置页签首屏统一成同一套“处置闭环卡”口径。

当前剩余的不一致点主要在于三类支撑视图仍各自展示“责任归口”信息：

1. 处置闭环卡展示的是闭环责任摘要。
2. 处置记录卡片单独展示一条“最近责任归口”文本。
3. 生命周期轨迹中的处置节点也单独展示一条责任说明。

这会让资产管理员在同一详情页里看到三种相近但并不完全统一的责任信息表达。

## 2. 本批目标

第六批只做一件事：把生命周期处置节点、处置记录卡片、处置闭环卡统一为同一套“最近动作责任链”视图。

实现后需要满足：

1. 三处视图都复用同一套责任链解释器。
2. 三处视图都使用“最近动作 / 责任归口 / 责任动作 / 最近责任人”这一组固定字段。
3. 生命周期节点与记录卡片不再维护独立文案拼接逻辑。
4. 本批继续只做前端隔离层，不修改处置后端脏文件。

## 3. 方案选择

### 方案A：统一最近动作责任链视图（采用）

做法：

1. 在 disposal-overview.ts 中抽出共享的 DisposalResponsibilityChain 视图模型。
2. 闭环卡、记录卡片、生命周期节点都调用同一套构造方法。
3. 新增共享组件 disposal-responsibility-chain.vue，支持卡片模式与行内模式。

优点：

1. 责任归口口径完全统一。
2. 改动仍然只落在不动产详情壳前端层。
3. 后续如果继续强化责任链提示，只改一处解释器即可。

### 方案B：只增强生命周期节点

优点：改动最少。

缺点：记录卡片和闭环卡仍然保留另一套字段表达，不符合本批目标。

### 方案C：直接新建处置责任组件但保留各自解释逻辑

优点：模板层统一较快。

缺点：脚本层仍然是三套逻辑，后续仍然容易漂移。

## 4. 设计结果

### 4.1 统一责任链视图模型

在 disposal-overview.ts 中新增 DisposalResponsibilityChain，固定包含：

1. ecentActionLabel
2. ecentActionTime
3. ownerLabel
4. ctionLabel
5. latestOwnerLabel
6. hint

并新增三个构造入口：

1. uildDisposalResponsibilityChain
2. uildDisposalRecordResponsibilityChain
3. uildDisposalLifecycleResponsibilityChain

### 4.2 共享责任链组件

新增 disposal-responsibility-chain.vue：

1. card 模式给闭环卡使用。
2. inline 模式给记录卡片和生命周期节点使用。
3. 行内模式统一展示：
   - 最近动作责任链：xxx · 责任归口：xxx · 责任动作：xxx · 最近责任人：xxx
4. 卡片模式保留责任提示，强化首屏说明。

### 4.3 闭环卡统一责任链

闭环卡不再自己展示三格责任字段，而改为嵌入共享责任链组件。

这样闭环卡、记录卡片、生命周期节点三处在视觉上和字段层面都来自同一套解释数据。

### 4.4 记录卡片统一责任链

处置记录卡片中的：

1. 最近责任归口
2. 责任动作
3. 最近责任人
4. 提示文案

全部改为通过共享责任链组件输出，避免继续拼接独立文案。

### 4.5 生命周期节点统一责任链

生命周期轨迹中的处置节点在阶段标签之外，继续补充同一套责任链行内视图。

这样用户在看“发起处置 / 提交审批 / 审批通过 / 确认处置”时，能立刻知道：

1. 这一步属于谁负责
2. 当前动作属于什么归口
3. 最近由谁执行

## 5. 风险与控制

### 5.1 风险

1. 共享责任链组件接入三处模板后，容易造成旧测试用例整体失效。
2. 生命周期节点和记录卡片的数据来源不同，若解释器边界不清晰，容易串线。

### 5.2 控制

1. 先补红灯测试，再做实现。
2. 生命周期和记录卡片分别提供独立构造入口，但底层仍复用统一解释器。
3. 不修改统一处置模块后端文件，继续保持隔离实现。

## 6. 验收标准

1. 闭环卡、记录卡片、生命周期节点三处均显示“最近动作责任链”。
2. 处置责任链中的最近动作、责任归口、责任动作、最近责任人保持一致口径。
3. 定向测试与相关回归测试全部通过。
4. 本批不触碰处置后端脏文件和 pplication-druid.yml。
