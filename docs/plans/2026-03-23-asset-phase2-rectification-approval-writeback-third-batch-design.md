# 2026-03-23 不动产整改审批回写第三批设计

## 1. 背景

第二批已经把整改审批回写到整改单、整改页签、整改编辑页和整改完成页，资产管理员可以看到：
- 当前审批状态
- 最新审批意见
- 下一步该做什么

但站在“不动产详情页总览”视角，仍有两个明显缺口：
1. 资产管理员打开详情壳首页时，无法一眼判断当前整改闭环卡在“待整改 / 待提交审批 / 审批中 / 驳回待重提”的哪一段。
2. 生命周期轨迹虽然已经保留整改和审批动作，但仍然以原始变更说明为主，整改关键节点不够突出，判断最近一次整改闭环动作仍然费劲。

因此第三批不增加新的审批动作，而是聚焦“详情壳收紧”：把整改闭环的核心判断前移到总览，并把生命周期轨迹中的整改节点解释清楚。

## 2. 目标

第三批目标只做两件事：
1. 在不动产详情壳总览中增加整改闭环摘要，帮助资产管理员一眼识别当前闭环状态和最近一次整改动作。
2. 收紧生命周期轨迹，让“发起整改 / 完成整改 / 提交审批 / 审批通过 / 审批驳回”这些节点在总览里更容易被识别。

## 3. 非目标

本批明确不做以下内容：
- 不增加新的整改审批动作
- 不接入正式审批流引擎
- 不扩展处置主线
- 不修改处置相关脏文件
- 不新增 SQL
- 不改动 `application-druid.yml`

## 4. 方案选择

### 方案 A：只补总览文案
- 优点：改动最小
- 缺点：生命周期轨迹仍然是原始日志，关键节点还是不够清楚

### 方案 B：总览摘要 + 生命周期整改节点解释层（推荐）
- 优点：返工最少，复用第二批已有审批阶段字段，不需要新增接口
- 缺点：需要补一层前端摘要和轨迹解释逻辑

### 方案 C：新增整改闭环聚合接口
- 优点：结构更独立
- 缺点：会新开接口和聚合逻辑，收益不如当前投入

推荐采用方案 B。

## 5. 设计

### 5.1 详情壳概览收紧
在详情壳头部摘要增加“整改闭环”状态，让资产管理员留在详情首页时就能知道：
- 当前整改闭环总体卡点
- 是否仍存在未收口整改

同时在总览页新增“整改闭环摘要”卡片，展示：
- 待整改数
- 待提交审批数
- 审批中数
- 驳回待重提数
- 审批通过数
- 最近一次整改动作
- 当前下一步建议

### 5.2 生命周期轨迹收紧
在总览页生命周期轨迹中识别整改关键节点：
- 发起整改
- 完成整改
- 提交审批
- 审批通过
- 审批驳回

展示方式：
- 在轨迹项中增加阶段标签
- 补一条简短节点解释，避免只能看原始 `changeDesc`
- 仍保留原始变更说明，方便审计回看

### 5.3 现有整改轨迹同步收口
详情壳里给整改页签传入的 `rectificationLogs` 过滤范围从“只看包含整改”调整为“整改 + 审批”，保证驳回/通过节点也能进入整改轨迹。

## 6. 数据来源

本批继续复用现有生命周期数据：
- `rectificationOrders`
- `changeLogs`

不新增后端字段。

整改闭环摘要中的阶段判断继续复用第二批已经统一好的审批阶段逻辑：
- 待整改
- 待提交审批
- 审批中
- 审批驳回待重提
- 审批通过，已完成闭环

## 8. 风险与控制

### 风险 1：总览信息过重
- 控制：摘要只保留计数、最近动作和下一步建议，不把整改页签整段搬进总览

### 风险 2：整改节点识别不稳定
- 控制：只对固定关键词做解释层增强，无法识别的轨迹仍按普通生命周期记录展示

### 风险 3：整改页签轨迹口径与总览不一致
- 控制：统一把整改相关的审批节点也纳入 `rectificationLogs`

## 9. 预期结果

完成后，资产管理员打开不动产详情页总览时，可以直接判断：
- 当前是否还有整改未闭环
- 已完成整改的记录是否卡在审批阶段
- 最近一次整改闭环动作是什么
- 接下来优先该推进“整改事实收口 / 提交审批 / 跟进审批 / 根据驳回意见重提”中的哪一步

这样第三批会把“不动产整改闭环”从整改页签进一步收紧到详情壳总览，闭环判断成本更低。
