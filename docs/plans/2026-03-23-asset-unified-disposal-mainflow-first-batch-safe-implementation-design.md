# 统一处置主流程第一批安全实现设计

## 1. 背景

基于当前不动产主线实现检查点，处置线已经在“不动产详情壳”这一层完成了 1~6 批隔离闭环：

1. 顶部摘要、总览、处置页签已能识别处置闭环状态。
2. 责任归口、最近动作、最近责任人已经统一。
3. 详情壳与统一处置页之间的跳转上下文已经稳定。
4. 已补真实处置样例并完成浏览器点测。

但这仍然不是“统一处置主流程”本身的正式闭环。当前真正缺的，是：

1. 统一处置页如何稳定承接来自不动产的来源上下文。
2. `intent=start` 和 `intent=view` 两种来源意图如何在统一处置页中做清晰分流。
3. 如何在不触碰当前后端处置脏文件的前提下，先把统一处置页前端接入做安全。

## 2. 第一批目标

第一批不追求把统一处置主流程完整做完，而是只做“安全接入层”：

1. 统一处置页明确识别来自不动产的来源上下文。
2. 统一处置页根据 `intent` 决定首屏落点与提示方式。
3. 页面提供明确的“返回不动产详情”路径。
4. 当前资产范围在统一处置页中被稳定锁定与解释。
5. 全程只改前端，不改后端，不加 SQL。

一句话概括：

> 第一批要先把“统一处置页怎么安全接住不动产详情壳传来的意图”做扎实。

## 3. 方案对比

### 方案 A：前端安全接入批（采用）

做法：

1. 统一处置页解析并归一化来源上下文参数。
2. 页面新增来源横幅、资产上下文卡、返回入口。
3. `intent=start` 和 `intent=view` 只影响前端首屏体验与当前页签落点，不触碰后端流程。
4. 利用现有处置页已有能力承接后续动作。

优点：

1. 风险最低。
2. 不会碰当前处置后端脏文件。
3. 能先把“入口层体验”和“来源语义”稳定下来。

缺点：

1. 还没有进入统一处置主流程内部的正式业务改造。

### 方案 B：直接进入统一处置后端正式建单与审批主流程

优点：

1. 业务上一步到位。

缺点：

1. 当前工作区后端处置脏文件较多，碰撞风险最高。
2. 一开始就进入深水区，不适合作为第一批。

### 方案 C：继续只停留在不动产详情壳

优点：

1. 风险最低。

缺点：

1. 这不再解决当前真正缺口。
2. 统一处置页仍然没有形成清晰来源接入层。

## 4. 最终方案

采用方案 A：前端安全接入批。

### 4.1 核心原则

1. 先做统一处置页的来源语义和入口承接。
2. 不新增后端接口。
3. 不改处置后端主流程。
4. 让不动产来源用户进入统一处置页时，知道“我从哪里来、为什么来到这里、下一步该点哪里”。

## 5. 第一批范围

### 5.1 来源上下文解析层

新增一个轻量前端解释层，负责统一解析以下参数：

1. `source`
2. `intent`
3. `assetId`
4. `assetCode`
5. `assetName`

并产出稳定视图模型：

1. 来源标签
2. 来源说明
3. 当前资产上下文标题
4. 当前返回入口信息
5. 默认页签建议
6. 当前筛选锁定说明

### 5.2 统一处置页首屏增强

在统一处置页增加：

1. 来源横幅
2. 当前资产上下文卡
3. 返回不动产详情按钮
4. 当前筛选锁定说明

### 5.3 `intent` 分流

#### `intent=view`

1. 默认停留在 `record` 页签。
2. 强调“当前已按资产过滤处置记录”。
3. 提供返回详情壳入口。

#### `intent=start`

1. 优先引导到能继续处置推进的入口。
2. 如果当前资产已进入处置池，首屏应给出“继续提交处置”提示。
3. 如果当前资产已存在处置记录，则给出“查看当前记录”提示。
4. 不直接改后端状态，只做来源驱动的前端分流。

### 5.4 不动产来源样式边界

第一批不做复杂 UI 重构，只做以下增强：

1. 信息层级更清楚
2. 来源与返回路径更清楚
3. 资产上下文更明确
4. 不影响原有统一处置页的普通使用路径

## 6. 安全改动边界

### 6.1 本批允许改动

推荐只动以下文件：

1. `art-design-pro/src/views/asset/disposal/index.vue`
2. `art-design-pro/tests/views/asset-disposal-page.test.ts`
3. 新增：`art-design-pro/src/views/asset/disposal/disposal-source-context.ts`
4. 视情况新增：`art-design-pro/src/views/asset/disposal/components/disposal-source-banner.vue`
5. 本批设计/计划文档

### 6.2 本批明确不动

1. `RuoYi-Vue/ruoyi-admin/src/main/java/com/ruoyi/web/controller/asset/AssetDisposalController.java`
2. `RuoYi-Vue/ruoyi-asset/src/main/java/com/ruoyi/asset/service/impl/AssetDisposalServiceImpl.java`
3. `RuoYi-Vue/ruoyi-asset/src/main/resources/mapper/asset/AssetDisposalMapper.xml`
4. `RuoYi-Vue/ruoyi-admin/src/main/resources/application-druid.yml`
5. 任何新增 SQL

## 7. 风险与控制

### 风险 1：统一处置页已有逻辑较重，接入来源上下文时容易串 tab 行为

控制：

1. 先写前端测试。
2. 只围绕 query 参数和首屏行为做增强。
3. 不重构现有处置业务动作。

### 风险 2：`intent=start` 场景容易误导用户，以为已经创建处置单

控制：

1. 文案明确使用“继续发起 / 继续办理”，不使用“已创建”。
2. 只在前端做引导，不伪造后端状态。

### 风险 3：来源上下文可能影响普通资产处置用户

控制：

1. 所有来源增强都必须是“有来源参数才显示”。
2. 无来源参数时，统一处置页表现保持原样。

## 8. 验证口径

第一批完成后，至少需要验证：

1. 从不动产详情壳进入统一处置页时，能看到来源横幅和资产上下文。
2. `intent=view` 时默认落在记录页签，并保留资产过滤。
3. `intent=start` 时首屏提示与入口符合发起语义。
4. 存在返回不动产详情页的清晰入口。
5. 普通无来源参数进入统一处置页时，不受影响。
6. 不出现新的 Vue 警告。

## 9. 结论

统一处置主流程的第一批，不应该直接做后端建单与审批，而应该先完成“来源上下文安全接入层”。

这样后续真正进入处置主流程改造时，我们是在一个来源语义清晰、前端入口稳定、风险边界明确的基础上推进，而不是一上来就进入高碰撞区域。
