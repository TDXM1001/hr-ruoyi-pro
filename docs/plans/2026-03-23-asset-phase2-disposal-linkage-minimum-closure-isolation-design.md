# 不动产处置关联最小闭环隔离设计

## 1. 背景

当前不动产主线已经完成了建档、巡检整改、整改审批回写和占用闭环，但处置线仍停留在“详情页跳转到统一处置模块并带过滤条件”的阶段。

这意味着：

1. 不动产详情页可以看到历史处置记录。
2. 用户可以跳转到统一资产处置模块。
3. 但不动产侧还不能形成真正的处置闭环。

当前最明显的缺口包括：

1. 不动产侧无法直接发起处置。
2. 处置申请或处置记录的建立没有形成明确的资产详情入口。
3. 处置审批结果没有稳定回写到不动产详情壳。
4. 资产管理员在不动产详情页里无法直接判断“当前是否正在处置”“最近处置动作是什么”“下一步应该推进什么”。

同时，当前工作区里已经存在一批处置/审批相关脏文件，因此这条线当前的首要工作不应该是直接写实现，而是先做隔离设计，把后续安全改动边界定义清楚。

## 2. 目标

### 2.1 业务目标

让不动产详情页具备最小处置闭环能力，使资产管理员能够：

1. 在不动产侧发起处置。
2. 明确知道处置当前处于哪个阶段。
3. 在详情页中查看最近一次处置动作与下一步建议。
4. 在统一处置模块完成正式流程后，回到不动产详情页即可看到结果回写。

### 2.2 技术目标

1. 不重复建设第二套处置系统。
2. 不让不动产详情壳自己承载完整处置流程。
3. 保持“不动产域负责识别状态与发起动作，统一处置模块负责正式流程”的结构。
4. 在不触碰当前处置脏文件的前提下，先定义清楚后续实现边界。

## 3. 方案对比

### 方案 A：不动产侧轻发起，统一处置模块承接（推荐）

- 做法：
  - 不动产详情页只负责“发起处置意图”和“查看处置闭环摘要”。
  - 统一资产处置模块继续承担处置申请、审批、结果记录。
  - 不动产详情页回看处置状态和最近动作。
- 优点：
  1. 最符合现有系统结构。
  2. 不会把详情壳做成第二个处置系统。
  3. 返工最少。
- 风险：
  - 需要设计好“发起意图”和“结果回写”的边界。

### 方案 B：不动产详情内嵌迷你处置流程

- 做法：
  - 在不动产详情页内直接承载发起、审批、结果展示。
- 优点：
  - 用户路径短。
- 风险：
  1. 详情壳会持续膨胀。
  2. 与统一资产处置模块职责重叠。
  3. 后续几乎一定返工。

### 方案 C：单独建设不动产处置子模块

- 做法：
  - 在不动产域下再做一套 `real-estate-disposal`。
- 优点：
  - 表面上领域边界清楚。
- 风险：
  1. 和统一资产处置模块重复建设。
  2. 当前阶段明显过重。

## 4. 最终方案

采用方案 A：不动产侧轻发起，统一处置模块承接。

## 5. 最小闭环范围

### 5.1 不动产详情页

不动产详情页新增“处置闭环摘要”，至少展示：

1. 当前是否已发起处置。
2. 当前处置阶段。
3. 最近一次处置动作。
4. 下一步建议。

### 5.2 发起入口

在不动产详情页的处置页签内新增“发起处置”入口，点击后带着完整资产上下文进入统一处置模块。

资产上下文至少应包括：

1. `assetId`
2. `assetCode`
3. `assetName`
4. 当前资产状态
5. 不动产处置来源标识

### 5.3 统一处置模块

统一处置模块承接：

1. 处置申请建立
2. 最小审批推进
3. 处置记录生成
4. 处置完成结果沉淀

### 5.4 回写

处置流程推进后，需要回写到不动产详情页，至少包括：

1. 处置状态
2. 最近处置动作
3. 生命周期日志中的处置节点
4. 必要时回写资产状态

### 5.5 详情回看

不动产详情页中的“处置”页签不再只是一个跳转按钮，而是要成为一个可判断当前闭环状态的轻摘要页：

1. 可发起
2. 可查看当前状态
3. 可查看最近动作
4. 可查看历史处置记录
5. 可继续跳转到统一处置模块做正式处理

## 6. 页面分工

### 6.1 不动产详情壳负责

1. 处置闭环摘要
2. 发起处置入口
3. 最近动作展示
4. 历史记录回看
5. 生命周期节点回看

### 6.2 统一处置模块负责

1. 处置表单
2. 审批动作
3. 审批记录
4. 处置结果确认
5. 正式业务闭环处理

## 7. 状态流转建议

建议最小闭环状态只定义为：

1. `NOT_STARTED` 未发起处置
2. `PENDING_SUBMIT` 待提交处置申请
3. `IN_REVIEW` 处置审批中
4. `REJECTED_RESUBMIT` 驳回待重提
5. `APPROVED_DISPOSING` 审批通过待完成处置
6. `DISPOSED_CLOSED` 已完成处置闭环

说明：

- 这套状态只服务于“不动产详情壳的摘要表达”。
- 不要求当前立即重构统一处置模块内部的全部状态。
- 重点是让不动产侧能稳定表达阶段，而不是现在就统一全系统状态机。

## 8. 安全改动边界

这轮隔离设计明确以下边界：

1. 当前不直接实现处置代码。
2. 当前不触碰你工作区里已有的处置/审批脏文件。
3. 当前不触碰 `application-druid.yml`。
4. 当前只产出设计文档与实施计划。

后续真正实现时，建议优先从下面几类位置下手：

1. 不动产详情页自身的适配层
2. 新增的状态解释工具
3. 新增测试
4. 必要时新增隔离式对接层

不建议一开始直接改已有处置核心实现文件。

## 9. 风险

### 风险 1：统一处置模块的现有状态口径与不动产侧摘要不一致

应对方式：

- 先在不动产侧定义“摘要状态映射层”。
- 不要求当前立即统一底层状态机。

### 风险 2：工作区处置脏文件冲突

应对方式：

- 后续实现前先确认隔离方式。
- 当前只做设计，不做落地实现。

### 风险 3：不动产详情壳过度膨胀

应对方式：

- 坚持只做“轻发起 + 摘要 + 回看”。
- 处置正式流程继续由统一模块承接。

## 10. 验证口径

后续进入实现时，最小验证应覆盖：

1. 不动产详情页可以发起处置。
2. 统一处置模块能接收到正确资产上下文。
3. 处置推进后，不动产详情页摘要可以看到状态变化。
4. 最近处置动作和生命周期节点可回看。
5. 处置页签不再只是单纯跳转卡片。

## 11. 结论

这条线当前最合理的推进方式不是直接开做，而是先把边界设计清楚：

- 不动产详情壳负责发起和摘要
- 统一处置模块负责正式流程
- 通过最小状态映射与结果回写，把处置真正纳入不动产主线闭环

这会比直接把处置流程塞进不动产详情页更稳，也比现在继续只做“跳转联动”更完整。
