# 2026-03-23 不动产占用逻辑基线梳理

## 1. 为什么要先梳理这份文档

当前不动产主线里，占用模块已经连续做了多批增强。站在资产管理员视角，这会带来一个真实问题：

1. 看得见很多按钮和治理能力
2. 但不容易一眼看清“占用”到底在解决什么业务问题
3. 也不容易分辨哪些是核心闭环，哪些只是管理增强

所以第十八批不应该直接继续堆功能，而应该先把占用逻辑重新校准。只有核心边界清楚，后续实现才不会继续发散。

## 2. 占用模块到底在解决什么问题

占用模块本质上只回答 4 个问题：

1. 这项不动产当前是谁在使用
2. 从什么时候开始由这个部门和责任人使用
3. 中途是否发生过使用归口、责任人或位置变化
4. 什么时候释放，释放后是否还存在当前有效占用

换句话说，占用不是在做空间管理，不是在做审批中心，也不是在做 BI 分析。它首先是一个“当前使用归口 + 历史轨迹”的业务闭环。

## 3. 占用核心业务闭环

结合现有设计和代码，占用的核心闭环只有 3 个动作。

### 3.1 发起占用

适用场景：当前资产没有有效占用，但需要明确当前由哪个部门、哪个责任人、在哪个位置使用。

进入条件：

1. 资产存在
2. 资产类型是不动产
3. 当前不存在有效占用

完成结果：

1. 新建一条有效占用记录
2. 回写资产主档当前使用部门、责任人、位置
3. 资产状态进入“使用中”
4. 进入生命周期与变更日志

### 3.2 变更占用

适用场景：资产仍在使用，但使用部门、责任人或位置发生调整。

进入条件：

1. 当前必须存在一条有效占用
2. 只能对这条有效占用做变更

完成结果：

1. 旧占用关闭为已释放
2. 新建一条新的有效占用
3. 资产主档同步为新的使用快照
4. 生命周期中形成一条完整的变更轨迹

这一步非常关键。

占用变更不是“修改原记录”，而是“关闭旧记录，再生成新记录”。这样才能保留审计轨迹，知道资产在不同时间由谁占用。

### 3.3 释放占用

适用场景：当前这项不动产不再被任何部门和责任人实际占用。

进入条件：

1. 当前必须存在一条有效占用
2. 只能释放这条有效占用

完成结果：

1. 当前有效占用变为已释放
2. 资产主档清空当前使用部门、责任人、位置
3. 资产状态回到“闲置中”
4. 生命周期留下释放轨迹

## 4. 占用的真实状态机

从业务角度看，占用本身只有两种状态：

1. `ACTIVE`：有效占用
2. `RELEASED`：已释放

同时，资产主档会跟着占用同步两种主状态：

1. 有有效占用时：`IN_USE`
2. 无有效占用时：`IDLE`

因此，占用线的核心规则其实很简单：

1. 一项资产同一时刻只能有一条有效占用
2. 变更占用 = 关闭旧有效占用 + 新建新有效占用
3. 释放占用 = 关闭当前有效占用 + 清空资产主档使用快照

## 5. 代码里已经做到哪里了

从当前代码来看，占用的核心业务闭环其实已经完成。

### 5.1 后端闭环已经完成

后端已经具备 4 个核心接口：

1. 查询占用记录
2. 发起占用
3. 变更占用
4. 释放占用

而且服务层已经把核心状态机做实：

1. 发起占用前会校验当前是否已有有效占用
2. 变更占用时会先关闭旧记录，再新建新记录
3. 释放占用时会把当前记录改为已释放
4. 每次动作都会同步资产主档当前使用快照
5. 每次动作都会写入变更日志

这说明从业务实现角度看，占用不是“还没闭环”，而是“核心闭环已经存在”。

### 5.2 前端业务操作闭环也已经完成

前端详情页的占用页签，已经具备业务闭环所需的核心入口：

1. 当前有效占用卡片
2. 变更占用入口
3. 释放占用入口
4. 历史占用轨迹
5. 无有效占用时的发起占用入口

也就是说，从资产管理员真正操作业务的角度，最小闭环已经成立。

## 6. 为什么会感觉“占用做了很多”

这是这次梳理最重要的结论。

原因不是核心业务还没做完，而是后续多批工作已经从“业务闭环”延伸到了“管理增强”和“治理分析”。

### 6.1 第一层：核心业务闭环

这是占用必须有的部分：

1. 发起占用
2. 变更占用
3. 释放占用
4. 资产主档回写
5. 生命周期轨迹

这部分是必须做的，也是占用存在的核心价值。

### 6.2 第二层：管理增强

这是为了让资产管理员更容易看和更容易操作：

1. 当前占用摘要
2. 主档联动摘要
3. 最近一次变更摘要
4. 历史筛选
5. 空态引导

这部分是合理增强，但本质上还是服务核心业务。

### 6.3 第三层：治理分析

这部分就是你现在感觉“为什么做了这么多”的主要来源。它包括：

1. 来源链路统计
2. 趋势图
3. 导出字段配置
4. 自定义预设
5. 批注视图
6. 导入预览
7. 冲突处理策略
8. 趋势快照
9. 治理活动流
10. 治理审计包

这些能力不是新的业务步骤，而是围绕占用轨迹做的治理和分析工具。

所以你看到“占用一直在做”，并不代表占用主流程一直没做完，而是因为我们后面持续在做占用的治理层。

## 7. 当前判断：占用已经做到哪一层

如果按业务价值分层，当前状态应该这样判断。

### 7.1 核心闭环：已完成

已经具备：

1. 发起
2. 变更
3. 释放
4. 回写
5. 留痕

这说明占用作为“不动产主线的一个业务段落”，已经不是缺失状态。

### 7.2 管理增强：已较完整

已经具备：

1. 摘要卡片
2. 空态提示
3. 历史筛选
4. 连续操作入口

这部分已经足够支撑资产管理员日常使用。

### 7.3 治理分析：已偏重

现在治理分析能力已经明显超出“占用最小闭环”的需要。

这不代表这些功能没有价值，而是说明：

1. 它们更像高级治理工具
2. 不应再被理解为“占用主流程本身”
3. 后续如果继续沿这条线扩展，需要先确认是否真有持续使用场景

## 8. 对第十八批的建议

第十八批我不建议继续直接加新的占用功能点。

更合理的做法是先做“占用模块收口批”，目标是把边界整理清楚。

### 方案 A：收口梳理并保留现状（推荐）

做法：

1. 保留当前核心闭环
2. 保留合理的管理增强
3. 把治理分析统一明确为“治理工具区”
4. 暂停继续追加新的占用治理功能

优点：

1. 不推翻已有工作
2. 用户认知会清晰很多
3. 不再让占用继续失焦

### 方案 B：对占用页签做减法

做法：

1. 核心操作保留在主视图
2. 治理分析默认折叠甚至部分隐藏
3. 让占用页签重新回到“业务优先”

优点：

1. 页面更轻
2. 更符合资产管理员的日常操作习惯

缺点：

1. 需要再做一轮前端减法整理

### 方案 C：占用先停止扩展，切回主线其他闭环

做法：

1. 将占用判断为“阶段性完成”
2. 暂停占用后续批次
3. 把资源切回处置关联或其他更核心的未闭环主线

优点：

1. 更符合当前整体项目推进效率
2. 避免在一个已闭环模块上继续过度投入

## 9. 本次梳理结论

一句话总结：

占用这条线的核心业务逻辑已经完成，后面之所以持续在做，主要是在做前端治理和分析增强，而不是因为占用主流程还没有闭环。

因此，第十八批最合理的方向不是继续“加占用功能”，而是先决定：

1. 是把占用收口并降噪
2. 还是停止扩展，占用视为阶段性完成

在这个判断做完之前，不建议继续往占用页签里叠新的功能点。
